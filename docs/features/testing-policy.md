# E2E テスト設計方針 (E2E Testing Policy)

## 1. 概要

`cderun` では、実際のコンテナランタイム環境における動作を保証するため、Docker の複数バージョンを用いた E2E テストを実施している。
本ドキュメントでは、E2E テストの設計思想、CI 構成、およびテスト拡充の際のガイドラインを定義する。

## 2. Docker バージョン別のリアルテスト

### 2.1. docker:dind の採用理由

`cderun` は Docker API を直接操作し、ボリュームマウントやデバイスマウント、ネスト実行などの高度な機能を提供する。これらの挙動は、Docker デーモンのバージョンや環境（ストレージドライバ等）によって微妙に異なる場合がある。
モックを用いたテストではこれらの差異を検出できないため、GitHub Actions のサービスコンテナとして `docker:dind` (Docker-in-Docker) を採用し、実際のデーモンに対してテストを実行する。

### 2.2. マトリックス戦略

以下の 3 つの世代を主要なターゲットとして継続的に検証する。

- **20.10**: 旧安定版。レガシーな環境との互換性維持を確認する。
- **24.0**: 現在広く普及しているバージョン。
- **27.0**: 最新版。最新の API 挙動やセキュリティアップデートへの対応を確認する。

## 3. CI 環境特有のパス解決

### 3.1. ホストパス vs DinD コンテナパス

GitHub Actions で DinD を使用する場合、テストを実行する Runner (ホスト) と、Docker デーモンが動作する DinD コンテナは別物である。
Runner 上のファイルをコンテナにマウントする場合、Docker デーモンからは Runner のパスが直接見えない。

この課題を解決するため、以下の対策を講じている。

1. **共通ボリュームのマウント**: GitHub Actions のワークフロー設定において、Runner のワークスペース (`/home/runner/work`) を DinD コンテナの同じパスにマウントしている。
2. **一時ディレクトリの制御**: テストコード内で `t.TempDir()` を使用する際、そのベースパスを環境変数 `TEST_HOST_TMP_DIR` で指定可能にしている。CI 環境では、この変数に Runner と DinD で共有されているパスを指定することで、マウントの整合性を保つ。

## 4. E2E テスト実装ガイドライン

新しく E2E テストを追加する際は、以下のルールに従うこと。

### 4.1. 基本ルール

- **ビルドタグ**: ファイル先頭に `//go:build e2e` を付与し、通常のユニットテストから分離する。
- **ヘルパーの利用**: `internal/command/test_helpers_test.go` に定義された `runCderun` や `skipIfDockerBroken` を活用する。
- **クリーンアップ**: `t.Cleanup()` を使用し、テストで使用したリソースを確実に解放する。

### 4.2. リアルな Docker 環境の利用

- **診断モードの活用**: `TestE2E_DockerVersion` のように、`--diagnosis` モードを使用して、テストが期待したバージョンの Docker に対して実行されているかを常に確認可能にする。
- **ネスト実行 (DooD) の検証**: `cderun` の特徴であるネスト実行をテストする場合、ホストの Docker ソケット（または `DOCKER_HOST`）と `cderun` バイナリ自体をコンテナにマウントし、「コンテナ内からコンテナを起動する」フローを検証する。
- **環境依存の許容**: Docker のストレージドライバ（OverlayFS 上の OverlayFS など）の制限により、特定のマウント操作が失敗する場合がある。その際は `skipIfDockerBroken` を使用して適切にスキップし、テスト全体を失敗させないようにする。

## 5. 検証範囲 (全モード)

E2E テストでは以下のコア機能を必須の検証対象とする。

1. **標準実行**: コンテナの起動、コマンド実行、出力の取得。
2. **ネスト実行**: `Host -> Container A -> Container B` の 2 段階実行。
3. **ボリュームマウント**: ホスト・コンテナ間のファイル読み書き。
4. **診断モード (`--diagnosis`)**: ランタイム検出機能の正常性。
5. **ドライラン (`--dry-run`)**: 生成される中間表現の構造的整合性。
