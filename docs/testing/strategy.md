# テスト戦略 (Testing Strategy)

## 1. 目的とスコープ

このドキュメントは **「cderun のテストはこうあるべき」の定義** であり、`docs/testing/` 配下の他ドキュメント（`organization.md`, `integration.md`, `runtime-tests.md`, `coverage.md`）の上位方針である。テストの追加・修正・レビューは、すべて本ドキュメントの原則に従う。

背景: 本プロジェクトのテストは量的には充実しているが、「コードの行を実行すること」を目標としたテスト（カバレッジ駆動）が多く、「仕様を破ったら落ちること」を保証するテスト（振る舞い駆動）が不足していた。実際に、大量のユニットテストが存在しながら引数解析の挙動差異を判別できなかった事例がある（`.agent/todo.md` の T44 を参照）。本戦略はこの構造を転換する。

## 2. 基本原則

1. **テストの正は仕様である。**
   テストの存在意義は「`docs/features/*.md` に書かれた挙動を壊したときに落ちること」である。テストケース（またはテスト関数）は、対応する仕様ドキュメントの節をコメントで参照すること。仕様に書かれていない挙動をテストで固定したい場合は、先に仕様ドキュメントへ追記する（Document-First）。
2. **カバレッジは結果であって目的ではない。**
   行カバレッジの向上自体を動機としたテストの新規追加を **禁止** する。ファイル名・テスト名に `coverage` を含む新規テストは追加しない。網羅性の指標は「仕様条項のトレース率」と「mutation score」（第6節）を用いる。
3. **境界でテストする。**
   内部関数の単体テストより、安定した境界に対するテストを優先する。cderun の安定した境界は次の2つ:
   - **CLI 境界**: 引数 + 設定ファイル → `--dry-run` 出力（解決パイプライン全体の観測点）
   - **ランタイム境界**: `ContainerConfig` → `ContainerRuntime` インターフェースの各実装
   実装のリファクタリングで壊れないテストが良いテストである。
4. **全ランタイムは同じ振る舞いをする（コンフォーマンス）。**
   `ContainerConfig` からコンテナの観測可能な挙動への変換は、Docker / Podman / containerd / Mock のすべての実装が共通の契約テストに合格しなければならない。ランタイムが未対応の機能は「黙殺」ではなく「明示エラー」であること自体を契約に含める。
5. **決定性を守る。**
   `time.Sleep` や実時間・実ネットワークに依存するテストを書かない。時刻・乱数・環境は注入可能にする。flaky なテストは quarantine（ビルドタグ等で隔離）した上で必ず起票し、放置しない。リーク防止は `integration.md` の指針に従う。

## 3. テストレイヤー

| レイヤー | 目的 | 手段 | 実行タイミング |
| :--- | :--- | :--- | :--- |
| **L1: ユニット** | 解決ロジック・パース・バリデーションの網羅 | テーブルドリブン。優先順位解決は registry メタデータから **機械生成** したマトリクスで全オプションを検証 | 毎 PR |
| **L2: ゴールデン** | 引数解析〜設定解決パイプライン全体の回帰検知 | 「CLI 呼び出し + 設定ファイル」のコーパス → `--dry-run --dry-run-format json` 出力のスナップショット比較 | 毎 PR |
| **L3: コンフォーマンス** | ランタイム実装間のパリティ保証 | `ContainerRuntime` の契約テストスイートを Mock（毎 PR）+ 実ランタイム（CI ジョブ）で共通実行 | 毎 PR (Mock) / CI (実) |
| **L4: E2E** | TTY・シグナル・attach・ライフサイクルの実挙動 | 実ランタイム + PTY（`creack/pty` 等）。`-tags=runtime` | CI / 夜間 |
| **横断: mutation** | 「壊したら落ちるか」の測定 | gremlins 等による mutation testing | 夜間 / 週次 |

## 4. 何をどこでテストするか

| 対象 | 主レイヤー | 補足 |
| :--- | :--- | :--- |
| 引数解析・ホイスト・サブコマンド検出 | L2 (+L1) | 判別力のあるケース（値付きフラグ + P1 フラグの組み合わせ等）を必ず含める |
| P1〜P6 優先順位解決 | L1 マトリクス + L2 | registry を single source of truth として生成（T05/T06 と統合） |
| 式解決・パス検証・マスキング | L1 | 境界値・セキュリティケースはテーブルに明記 |
| `ContainerConfig` → ランタイム変換 | L3 | 未対応機能の明示エラーも契約に含める |
| TTY・シグナル・attach・hang-timeout | L4 | flakiness を許容する代わりに quarantine 運用を厳格に |
| イメージ pull・リトライ | L1 + L3 | エラー分類（リトライ可否）はテーブルドリブン |

## 5. テスト作成チェックリスト（AI エージェント必読）

テストを書いたら、マージ前に以下を自問すること:

- [ ] このテストは `docs/features/*.md`（または本ドキュメント）のどの記述に対応するか、コメントで明示したか
- [ ] 実装の内部構造ではなく、**観測可能な挙動**を assert しているか
- [ ] 対象の挙動を意図的に壊したとき、このテストは**落ちるか**（自信がなければ実際に壊して確認する）
- [ ] カバレッジ向上だけが目的のテストになっていないか（なっているなら追加しない）
- [ ] `time.Sleep`・実時間・実ネットワーク・ホスト環境の暗黙依存がないか
- [ ] 命名は `organization.md` の規則に従っているか（`coverage` を含む名前は不可）

## 6. 指標

- **第一指標**: mutation score（生き残ミュータント数の削減）と、仕様条項のテストトレース率
- **参考指標**: 行カバレッジ。閾値は回帰検知（急落の検出）のためだけに使い、**目標値として掲げない**
- `coverage.md` の計測手順は引き続き有効だが、位置づけは本節に従う

## 7. 既存テストの移行方針

1. `*coverage*` 系のテストファイルは回帰価値があるため**即削除しない**
2. 仕様が明文化された領域から順に、対応する振る舞いテスト（L1/L2）へ吸収し、実装詳細に依存した重複テストを削除する
3. 新規テストでの `coverage` 命名は本日以降禁止（第2節）
4. 移行の進捗は `.agent/todo.md` の T72 で管理する
